# Security policy

## Reporting a vulnerability

Please do **not** open a public issue for a security problem.
Use GitHub's private reporting instead: **Security → Report a vulnerability** on this repository
(also listed in [`public/.well-known/security.txt`](public/.well-known/security.txt)).

Include what you found, how to reproduce it and, if possible, the impact. You will get an answer
as soon as the maintainer can read it, and the fix is published before details are shared.

## Supported version

Only the latest version on the default branch receives security fixes.

## Practices in this project

**Secrets and access**
- No secrets in the repository: `.env` is ignored, `.env.example` holds placeholders only.
- One access code per teacher (`ACCESS_CODES`), so a single code can be withdrawn without touching the others. Codes are checked in constant time.
- Placeholder codes (anything containing `CHANGE-ME`) are refused, so copying `.env.example` can never create a code that everyone knows.
- Any access setting means a code is required (the server fails closed), and production refuses to convert at all until one is set.
- Limits on wrong attempts: a client over the limit gets no further guesses, not even a correct one.

**Spending and abuse**
- Limits per hour per client, a daily budget per teacher and for the whole school, and a cache so the same PDF is never paid for twice.
- These limits are kept in a shared database (Upstash Redis) when one is configured, so every server instance counts together. Without it they work per instance, which is weaker. Set a monthly spend limit in the AI provider's console as well.
- Visitors are counted by a keyed hash of their IP address (`RATE_LIMIT_SECRET`). Raw addresses are never stored or logged.

**Browser and data handling**
- Strict HTTP security headers: a Content Security Policy that allows only the page's own script (by SHA-256 hash, no `unsafe-inline` for scripts), HSTS, `nosniff`, no framing, no referrer, minimal permissions.
- Everything that comes back from the AI service is validated and length-limited before use. A worksheet sent to be stored as a short link is validated again on the server.
- All text is escaped before it reaches the page; share links are size-limited; short-link IDs are 72 random bits.
- Everything read back from the browser's storage is validated again. A stored link must match the exact shape of a worksheet link.
- The service worker only handles `GET` requests to the site's own origin, never an upload or a conversion, and only keeps successful answers.
- The database address must be HTTPS, errors never include it or the token, and every stored item has an expiry.
- No third-party scripts, fonts, cookies or analytics.

**Project**
- No runtime dependencies, which keeps the supply-chain surface minimal.
- Automated tests run on every push and pull request.
- The CSP hash and the service worker are generated by `npm run build`, and a test fails if they are out of date.
- Hostile share links are limited in size and in decompressed size (zip-bomb protection).
- Provider error messages stay in the server log and are never shown to users.
- Serverless functions run in an EU region (Dublin).
- `main` is protected: changes need a pull request and a passing `test` check.

## If a code leaks

Delete that teacher's entry from `ACCESS_CODES` (or change `ACCESS_CODE`) in the hosting settings and redeploy. Anything already stored expires on its own: cached worksheets after `CACHE_TTL_DAYS`, short links after `SHARE_TTL_DAYS`. If an AI provider key leaks, create a new key in its console, replace `ANTHROPIC_API_KEY` and delete the old one.

See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for the full security design and [`docs/COMPLIANCE.md`](docs/COMPLIANCE.md) for the GDPR checklist.
